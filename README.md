# Автообновление программы РРФП 2026

Этот проект хранит только опубликованную программу и код её выгрузки. Сайт остаётся в Битрикс24. Доступ к Битрикс API и Airtable Automations не нужен.

## Что подготовлено

- `public/program.json` — текущая опубликованная программа.
- `public/program.last-good.json` — предыдущая успешная выгрузка.
- `scripts/` — выгрузка и проверка данных, Python 3.12 без дополнительных пакетов.
- `.github/workflows/program.yml` — ручной запуск и ежедневное обновление в 03:17 по Екатеринбургу (22:17 UTC предыдущего дня).

Начальные JSON содержат 57 мероприятий, включая описание IV Общероссийского конкурса. Данные взяты из последней проверенной публикации на сайте.

## Первоначальная настройка

1. Войти в GitHub. Создать **публичный** репозиторий `rrfp-2026-program-data` с основной веткой `master`. Для бесплатного GitHub Pages репозиторий должен быть публичным. В публичную историю попадут только опубликованная программа и код; токен туда не добавлять.
2. Загрузить содержимое этой папки в корень репозитория, сохранив пути `public/`, `scripts/` и `.github/workflows/program.yml`. Загрузка ZIP как одного файла не устанавливает проект. Если папка `.github` скрыта в Finder, нажать Cmd+Shift+точка или создать файл `.github/workflows/program.yml` через GitHub → Add file → Create new file.
3. В репозитории открыть **Settings → Pages → Build and deployment → Source → GitHub Actions**. До первого успешного запуска сайт Битрикса не менять.
4. В Airtable открыть [Personal access tokens](https://airtable.com/create/tokens). Создать отдельный токен `RRFP GitHub read-only` со scope **data.records:read** и доступом только к базе **RRFP 2026 Program**. Для скрипта не нужны права записи или чтения схемы. Создание и сохранение токена выполняет владелец аккаунта.
5. В GitHub открыть **Settings → Secrets and variables → Actions → New repository secret**. Имя **AIRTABLE_TOKEN**, значение — созданный токен. Вставлять его только в это закрытое поле, не в файлы и не в сообщения чата.
6. Открыть **Actions → Update RRFP programme → Run workflow**, ветка `master`, `refresh` включён. Дождаться зелёного результата обоих этапов.
7. Открыть адрес, показанный этапом `deploy`. Проверить `program.json` и `program.last-good.json`, а также загрузку JSON из страницы на `rrfp.ru` (важны CORS и доступность в браузере участников).
8. После проверки заменить в **текущем** HTML программы только `data-program-url` и `data-program-fallback-url` на адреса JSON в GitHub Pages. Формат адреса: `https://ИМЯ.github.io/rrfp-2026-program-data/program.json` и `.../program.last-good.json`. Сохранить нынешний HTML перед правкой. Другой интерфейс, CSS и скрипты оставлять как есть. Текущий код программы может отличаться от более ранних сохранённых шаблонов.
9. Проверить на сайте новое время выгрузки, описание конкурса, фильтры, карточку и «Мою программу». Старые служебные страницы Битрикса можно оставить как ручной резерв. Встроенный локальный JSON и кэш браузера продолжают работать.

## Как обновлять после настройки

Изменить данные в Airtable — они появятся на сайте после следующего успешного ночного запуска и открытия или перезагрузки страницы участником. Для срочных изменений нажать **Run workflow** с включённым `refresh`. Менять HTML в Битриксе каждый раз не нужно.

Если Airtable недоступен, выгрузка пустая или данные не проходят проверку, запуск завершится ошибкой и предыдущая опубликованная версия останется доступной. При недоступности GitHub Pages загрузчик сайта использует проверенный резерв, сохранённый кэш или встроенную локальную выгрузку.

Для ручной публикации уже готовых JSON заменить оба файла в `public/`, сохранив предыдущую успешную выгрузку в `program.last-good.json`. Коммит в `master` публикует эти файлы **без обращения к Airtable**. Можно также запустить **Run workflow** с выключенным `refresh`.

## Секции с перерывами

В поле Events → **Другое** укажите полный список рабочих интервалов, по одному на строку:

```text
**Время работы секции (с перерывами)**
12:30–14:30
15:00–17:00
17:30–19:30
```

**Начало** должно совпадать с началом первого интервала, **Окончание** — с концом последнего. Если оба поля времени пусты, выгрузка возьмёт общий диапазон из этого блока; поле **Дата** должно быть заполнено. Дальнейшие абзацы описания отделяйте пустой строкой, заголовки можно выделять жирным. Не записывайте в этот блок альтернативные или ещё не подтверждённые варианты времени.

В JSON добавлено необязательное поле `events[].intervals`: список объектов `start`, `end`, `startsAt`, `endsAt`. Время в `start`/`end` имеет вид `HH:MM`, полные даты содержат часовой пояс `+05:00`. У событий без такого блока список пуст. Прежние поля начала и окончания сохраняют общий диапазон, описание остаётся без изменений, а старые резервные JSON без `intervals` продолжают работать.

Если время содержит опечатку, интервалы пересекаются или общий диапазон с ними расходится, новый снимок не публикуется. Исправьте запись в Airtable и повторите запуск. Для отображения всех интервалов в карточке, расчёта пересечений и отдельных записей календаря код страницы должен использовать `intervals`; прежний код показывает общий диапазон и подробный текст описания.

## Ограничения расписания

Время запуска приблизительное: GitHub может задерживать запуски по расписанию. В публичных репозиториях GitHub отключает расписание после 60 дней отсутствия активности. При необходимости вернуть его через Actions → нужный workflow → Enable workflow. Ночные успешные выгрузки сохраняются в истории репозитория; это также даёт возможность восстановить старые версии данных.

При нынешних 57 мероприятиях и 15 спикерах обычный запуск делает два запроса к Airtable, около 60–62 запросов в месяц при одном запуске в сутки. Это не учитывает ручные запуски, повторные попытки и другие интеграции того же Airtable workspace.
